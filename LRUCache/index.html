LRU Cache – Low Level Design

A thread-safe, fixed-capacity cache with a pluggable eviction policy. Java.

Functional Non-functional Domain Architecture Components Flows Patterns Trade-offs

1. Functional requirements

  • put(key, value), get(key) (returns Optional), and remove(key).
  • The cache has a fixed capacity. When a new key pushes it over capacity, one entry is evicted.
  • The default rule is least recently used. Both reads and updating writes count as "use".
  • The eviction rule is swappable (LRU, FIFO, later LFU) without changing the cache code.
  • Observers can react to put, get and evict events (logging, hit-rate metrics).
  • A capacity of zero or less is rejected at construction.

2. Non-functional requirements

  • Performance: O(1) for get, put and remove.
  • Thread safety: concurrent callers must never corrupt the data or the ordering.
  • Consistency: the store and the eviction ordering must never disagree about what is cached.
  • Extensibility: new eviction rules, stores and listeners are added without editing the orchestrator.
  • Resilience: a slow or failing listener cannot break or block the cache.
  • Scope: single JVM, in-memory, generic <K, V>, no external libraries.

3. Domain identification

Reading the requirements as nouns and verbs gives the building blocks.

The key idea is separating where values live from which key to evict. They change for different reasons, so they get different classes.

5. Component responsibilities

ComponentResponsibility
CacheThe public contract: get, put, remove, size, capacity.
LRUCacheCoordinates store, policy and listeners. Holds the lock, checks capacity, triggers eviction, fires events. Contains no ordering logic.
CacheStore / InMemoryCacheStoreOwns the key-value data. Knows nothing about order or eviction. size() is the single source of truth for the count.
EvictionPolicyContract: keyAdded, keyAccessed, keyRemoved, evictionCandidate. Sees keys only, never values.
LRUEvictionPolicyHashMap plus doubly linked list. The most recent key sits at the head, the eviction candidate at the tail. All moves are O(1).
FIFOEvictionPolicyInsertion order only (LinkedHashSet). Ignores reads. It exists to show the strategy split really works.
CacheEventListenerHooks onPut, onGet, onEvict. Implementations: logging and atomic hit/miss/eviction counters.

6. Key flows

get(key)

  1. Lock.
  2. Read the value from the store.
  3. If found, call policy.keyAccessed(key).
  4. Unlock.
  5. Notify listeners (hit or miss).

put(key, value) on a full cache

  1. Lock. Write to the store.
  2. New key: policy.keyAdded. Existing key: policy.keyAccessed.
  3. If store.size() > capacity, ask the policy for a candidate.
  4. Remove it from the store first, then from the policy.
  5. Unlock. Notify put, then evict.

7. Design patterns used

PatternWhereWhy
StrategyEvictionPolicy and its implementationsEviction rules are mutually exclusive and chosen once at construction. Adding LFU means one new class, with no change to LRUCache.
ObserverCacheEventListenerAny number of listeners can react to events without the cache knowing about them or their logic.
RepositoryCacheStoreIsolates where data lives. An off-heap or memory-bounded store can replace the in-memory one with zero eviction changes.
Dependency injectionConstructor of LRUCacheThe wiring is explicit, and tests can pass in fakes.

Considered and rejected

  • Decorator: it fits behaviours that stack. Only one eviction policy applies at a time, so Strategy already expresses this.
  • Singleton: callers need many independent caches (per tenant, per resource type, isolated tests).
  • Facade class: there is no protocol translation at the boundary, so the interface plus its implementation is enough.

8. Trade-offs

DecisionGainCost
One ReentrantLock around each operationSimple and correct. Keeps store and ordering atomic. ConcurrentHashMap alone cannot do this because the work spans two structures.All callers serialize, even on reads, because a read also reorders. Throughput is limited under heavy contention. Sharding or striped locks would help.
Split store and policySwap either side freely. The policy is reusable for any value type.More classes and two structures that must stay in sync.
Remove from store first, then policyIf removal fails, state stays consistent.The cache can be briefly over capacity.
Notify listeners outside the lockA slow or throwing listener cannot block or corrupt the cache.Events are only eventually ordered. A listener may see an evict for a key that was already re-inserted.
Hand-written linked list, not LinkedHashMapGeneralizes beyond LRU and shows how it works underneath.More code. LinkedHashMap(accessOrder=true) is enough if LRU is the only policy ever needed.
In-memory, single JVMFast and simple.No coherence across servers. Multiple nodes need Redis or consistent hashing, which is an HLD problem.
Known limitations: null values are not supported because a null from the store means a miss. The class is named LRUCache but accepts any policy, so a name like PolicyCache would be more accurate.
